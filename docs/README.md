# AAS API Documentation Site

This directory contains the GitHub Pages site for hosting and rendering the Asset Administration Shell (AAS) OpenAPI specifications.

## Files

- **index.html** - Landing page with all API specifications organized by category
- **swagger-ui.html** - Interactive Swagger UI viewer for trying out APIs
- **redoc.html** - Documentation-focused Redoc viewer for reading APIs

## Features

### Landing Page (index.html)
- Categorized list of all API specifications
- Search functionality to find specific APIs
- Direct links to both Swagger UI and Redoc viewers
- Download links for raw YAML files
- Responsive design for mobile and desktop

### Swagger UI (swagger-ui.html)
- Interactive API documentation
- "Try it out" functionality to test endpoints
- Dropdown selector to switch between specifications
- Deep linking support
- Toggle between light/dark themes

### Redoc (redoc.html)
- Beautiful three-column layout
- Optimized for reading and reference
- Print-friendly
- Search within documentation
- Responsive sidebar navigation

## URL Structure

When deployed to GitHub Pages, the URLs will be:

```
https://[username].github.io/aas-specs-api/
https://[username].github.io/aas-specs-api/swagger-ui.html?url=../Entire-API-Collection/V3.2.yaml
https://[username].github.io/aas-specs-api/redoc.html?url=../Part1-MetaModel-Schemas/openapi_3.2.yaml
```

## Setup GitHub Pages

1. Go to repository Settings → Pages
2. Under "Source", select:
   - Branch: `main` (or your preferred branch)
   - Folder: `/docs`
3. Click Save
4. GitHub will provide your site URL (usually `https://[username].github.io/[repo-name]`)

## Local Development

**⚠️ Important:** You MUST serve from the **repository root** for the OpenAPI specs to load correctly.

The YAML files contain references like `../Part2-API-Schemas/openapi.yaml` which need access to the parent directory structure. Serving from `docs/` will cause "Could not resolve reference" errors.

### Correct Way (from repository root)
```bash
# From repository root
python3 -m http.server 8000
# Visit: http://localhost:8000/docs/
```

### Alternative Servers
```bash
# Node.js
npx http-server -p 8000
# Visit: http://localhost:8000/docs/

# PHP  
php -S localhost:8000
# Visit: http://localhost:8000/docs/
```

The JavaScript automatically detects the environment and adjusts the initial spec URLs, but the `$ref` references inside YAML files require proper directory structure access.

## Updating Documentation

The documentation automatically references the YAML files in the parent directories. When you update the YAML files in the repository, the documentation site will reflect those changes immediately - no rebuild required!

## Bundled Specs

The `github-pages` branch contains pre-bundled single-file variants of each Service Specification (SSP) YAML alongside the source files, named `bundled-V<ver>_SSP-<n>.yaml`. These are generated by [Redocly CLI](https://redocly.com/docs/cli/) and serve only the docs site — they are not normative and are not present on `main`.

**Why they exist:** Swagger UI 5.x fails to resolve cross-document `$ref`s (specifically `Reference.referredSemanticId → #/components/schemas/Reference`) when loading SSP YAMLs that import schemas from `Part1-MetaModel-Schemas/openapi.yaml` via relative paths. The recursive `Reference` schema was reintroduced in v3.2.0 and triggers the resolver bug there; it is absent in v3.0.x and v3.1.x. Redocly's bundler inlines all referenced schemas into the SSP document while preserving the self-referential `Reference` pointer byte-identical, eliminating the resolver errors.

**How the loader uses them (version-agnostic):** For any SSP path, `swagger-ui.html` first tries to load `../<ServiceDir>/bundled-V<ver>_SSP-<n>.yaml` and falls back to the original (raw-GitHub tag URL) on 404. In practice this means:

- Versions with bundled files present (v3.2 today) → bundled variant is loaded, no resolver errors.
- Older versions without bundled files (v3.0, v3.1) → fallback to the original raw-GitHub URL, same behaviour as before.
- Non-SSP entries (`Entire-API-Collection`, `Part1`, `Part2`) → never attempt the bundled lookup; load from the normal source.

**Adding new versions (v3.3, v4.0, …) — what is automated vs. manual:**

| Step | How |
|------|-----|
| Add/update the source `V<ver>_SSP-<n>.yaml` spec files on `github-pages` | **Manual** — these carry spec content, so a human decides what lands. |
| Update `DEFAULT_VERSION` in `assets/js/versions.js` and the default spec paths in `index.html` / `swagger-ui.html` / `redoc.html` (only when a new *current* major/minor replaces the specs) | **Manual** — deliberate one-off config change. |
| Regenerate the `bundled-V<ver>_SSP-<n>.yaml` files | **Automated** — see below. |

Only the bundling is automated: the script globs `V*_SSP-*.yaml`, so new versions are picked up with no code changes. Everything that authors spec content or switches the default version stays manual on purpose.

**Regenerating the bundled files (automated — default):** A GitHub Actions workflow, [`.github/workflows/bundle-specs.yml`](../.github/workflows/bundle-specs.yml), regenerates and commits the bundled files for you. It runs automatically whenever a source `V*_SSP-*.yaml`, either shared `openapi.yaml` schema, or the bundling tooling changes on `github-pages`. You no longer need to run the bundler by hand for normal updates. The workflow only ever regenerates derived `bundled-*.yaml` files — it never edits spec content and never touches `main`.

> The workflow pushes the regenerated `bundled-*.yaml` files directly back to `github-pages`. Configure a repo/org secret named `BUNDLE_PUSH_TOKEN` using a PAT or fine-grained token with **Contents: write**. This dedicated token is required because a push made with the default `GITHUB_TOKEN` does not trigger a branch-based GitHub Pages rebuild. If `github-pages` is protected, also allow the token's identity to bypass the push restriction.

**Regenerating (manual fallback):** If you need to regenerate locally (e.g. to debug), run from the repository root:

```bash
npm install          # install @redocly/cli (Node >= 20 required)
npm run bundle       # regenerates all bundled-V<ver>_SSP-*.yaml files
git add */bundled-V*_SSP-*.yaml
git commit -m "chore: regenerate bundled SSP files"
```

See [`scripts/bundle-specs.sh`](../scripts/bundle-specs.sh) for the full script.
